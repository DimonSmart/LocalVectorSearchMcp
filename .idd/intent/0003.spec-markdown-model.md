# 0003.spec-markdown-model

## Intent

Markdown documents are parsed from their exact source into logical elements with reliable source spans, addressed with revision-scoped semantic pointers, safely edited without reserializing untouched source, and grouped into section-bounded search chunks.

## Behavior

Only `.md` files are indexed and mutated. Loading preserves the exact source text, line endings, UTF-8 BOM when present, untouched whitespace, and exact-source SHA-256 `sourceHash`. New files are UTF-8 without BOM. Parsing is source-aware and assigns each exposed element an exact source span sufficient for targeted replacement.

Supported element kinds remain `Document`, `FrontMatter`, `Heading`, `Paragraph`, `CodeBlock`, `ListItem`, `Table`, and `BlockQuote`. The parser must reliably handle headings, paragraphs, fenced code, and front matter; lists and blockquotes must not corrupt surrounding spans even when represented using an existing compatible element kind.

Semantic pointers are deterministic logical addresses in one particular document revision, not persistent IDs. The canonical public document-root pointer is `document`; it addresses the whole Markdown document rather than the first heading and remains valid even for an empty document. External pointers use `relative/path.md::pointer`; internal pointers retain forms such as `document`, `frontmatter`, `p1`, `code1`, `1`, `1.p1`, `1.code1`, and `1.2.p3`. Section numbers follow heading order and nesting. Structural edits may change pointers; no paragraph UUIDs are added.

Semantic patch operations are `replace`, `insert_before`, `insert_after`, and `delete`. All operations in one patch resolve against the same source revision and are validated before any write. Missing pointers, stale source hashes, duplicate or otherwise conflicting target operations reject the whole patch. Source construction replaces or inserts only at validated spans and preserves every untouched byte-equivalent character; the document is not round-tripped through an AST serializer.

Chunks do not cross document or heading-section boundaries, keep code blocks intact, respect configured byte and element limits within a section, include heading context when configured, and produce stable embedding text hashes. A heading starts a new boundary; body content from two different heading sections cannot share a chunk.

Outline is a deterministic projection of parsed headings containing pointer, level, title, and nesting.

## Architecture And Patterns

Core defines source documents, spans, semantic pointers, elements, chunks, patch DTOs, outline DTOs, parser/validator APIs, and pure source patching rules. Infrastructure provides source loading and the Markdown parser implementation. Public mutation and read services operate on exact source revision hashes independently of MCP.

`MarkdownSourceDocument` contains relative path, absolute path, exact source Markdown, `SourceHash`, encoding/BOM information, and last-write time. Normalized text may be derived for hashing/search compatibility but cannot replace exact source for editing.

## Non-goals

Persistent element identities, full general-purpose Markdown editor AST serialization, automatic pointer relocation, automatic merge, and line-number-only addressing are excluded.

## Acceptance Criteria

- Exact source spans match LF, CRLF, UTF-8 BOM, headings, paragraphs, fenced code, and surrounding list/blockquote content.
- `sourceHash` changes for source-revision changes including EOL, BOM, whitespace, or other text.
- `document` is the canonical public document-root pointer; root reads begin with the first real source element and an empty document still has a valid root.
- Existing pointer forms remain valid and deterministic for a revision.
- Replace, insert-before, insert-after, and delete preserve untouched source formatting, EOLs, BOM, and whitespace.
- Multiple patch operations are atomic; missing, stale, duplicate, overlapping, or contradictory operations change nothing.
- Chunks never combine body elements from different heading sections.
- Embedding text retains path and heading context.
- Nested headings produce the expected pointer hierarchy and outline.

## Verification

- Unit-test exact-source loading, hashes, spans, pointer parsing, source patching, chunk boundaries, outline, and embedding text.
- Include LF/CRLF, BOM, headings, paragraphs, fenced code, lists, and blockquotes in parser tests.
