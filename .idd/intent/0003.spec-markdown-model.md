# 0003.spec-markdown-model

## Intent

Markdown documents are parsed from their exact source into logical elements with reliable source spans. Internal logical pointers remain deterministic structural addresses, while public concrete-element anchors add an exact-source fingerprint so semantic edits can tolerate unrelated document changes and structural shifts without persistent element IDs.

## Behavior

Only `.md` files are indexed and mutated. Loading preserves the exact source text, line endings, UTF-8 BOM when present, untouched whitespace, and exact-source SHA-256 `sourceHash`. New files are UTF-8 without BOM. Parsing is source-aware and assigns each exposed element an exact source span sufficient for targeted replacement.

Supported element kinds remain `Document`, `FrontMatter`, `Heading`, `Paragraph`, `CodeBlock`, `ListItem`, `Table`, and `BlockQuote`. The parser must reliably handle headings, paragraphs, fenced code, and front matter; lists and blockquotes must not corrupt surrounding spans even when represented using an existing compatible element kind.

A logical semantic pointer is a deterministic structural address such as `frontmatter`, `p1`, `1`, `1.p1`, or `1.2.p3`. Logical pointers remain the identity stored in parser, chunk, and SQLite structures. They may change after structural edits.

A public anchor for a concrete element has the canonical form `<logical-pointer>~<fingerprint>`. The fingerprint is XxHash64 over the UTF-8 representation of the element's exact source span, serialized as exactly 16 lowercase hexadecimal characters. Whitespace, line endings, Markdown syntax, case, and trailing spaces are not normalized. The special document-root pointer remains exactly `document` and has no fingerprint.

A fingerprint is derived revision metadata, not a persistent ID. It is not stored as a separate SQLite identity and no paragraph UUIDs are introduced. Public `kb_read`, `kb_search`, and `kb_outline` results expose fingerprinted anchors for concrete elements.

Fingerprint-aware resolution first checks the current element at the logical pointer. If kind and fingerprint match, that direct match wins even when identical elements exist elsewhere. Otherwise the resolver may relocate only by exact element kind plus exact fingerprint. Exactly one candidate is accepted. Zero candidates are stale, while multiple candidates are ambiguous. Fuzzy matching, edit distance, embeddings, surrounding-context heuristics, and LLM-assisted relocation are excluded.

Semantic patch operations are `replace`, `replace_element`, `replace_section`, `insert_before`, `insert_after`, and `delete`. Legacy `replace` is a deprecated alias of `replace_element`. Concrete-element mutations require a fingerprinted anchor. `document` remains unhashed and supports only `insert_before` and `insert_after`.

`replace_element` and legacy `replace` replace exactly one concrete editable element from the existing Markdown element model. Their replacement Markdown must parse to exactly one editable element. When the target is a heading, the replacement must also be a heading of the same level, so element replacement cannot implicitly restructure the document or consume the section body.

`replace_section` requires a fingerprinted heading anchor and replaces the heading plus its complete logical section. For a target heading of level N, the range extends from the target heading source start to the next heading with level <= N, exclusive, or to EOF. Nested headings with level > N belong to the section. The replacement must begin with a heading of the same level; every later heading in the replacement must be deeper than N. Section ranges are computed structurally from the current parsed revision after safe anchor resolution, while the raw source between boundaries is replaced so unsupported or non-indexed constructs inside the section are not left behind.

All operations in one patch resolve against one current source revision and are validated before any write. Resolved duplicate targets, missing or stale anchors, ambiguous relocation, overlapping edits, and contradictory operations reject the whole patch. A section replacement overlaps every operation whose source range falls inside that section; the next sibling boundary heading itself is outside the section and may be independently edited in the same patch. Source construction replaces or inserts only at validated spans, normalizes replacement EOLs to the current document, preserves BOM and every untouched byte-equivalent character, and does not round-trip the document through an AST serializer.

`sourceHash` is no longer a client concurrency token for `kb_patch`. It remains an internal exact-source guard between reading a patch attempt and atomically replacing the file. If the source changes during that window, the patch retries a bounded number of times from the newest source, including re-parsing and re-resolving all anchors. `sourceHash` also remains available for whole-file operations such as move and delete.

Chunks do not cross document or heading-section boundaries, keep code blocks intact, respect configured byte and element limits within a section, include heading context when configured, and produce stable embedding text hashes. A heading starts a new boundary; body content from two different heading sections cannot share a chunk.

Outline is a deterministic projection of parsed headings containing fingerprinted public pointer, level, title, and nesting.

## Architecture And Patterns

Core defines source documents, logical semantic pointers, public semantic anchors, fingerprinting and resolution rules, elements, chunks, patch DTOs, outline DTOs, parser/validator APIs, and pure source patching rules. Infrastructure provides source loading, Markdown parsing, SQLite-backed read/search adapters, and mutation orchestration.

`MarkdownSourceDocument` contains relative path, absolute path, exact source Markdown, `SourceHash`, encoding/BOM information, and last-write time. Normalized text may be derived for hashing/search compatibility but cannot replace exact source for editing.

The SQLite `elements.pointer` and `chunks.pointer` values remain logical pointers. Public fingerprints are computed from exact `elements.text` or current parsed `MarkdownElement.Text`; this behavior does not require a SQLite schema-version change.

## Non-goals

Persistent element identities, full general-purpose Markdown editor AST serialization, fuzzy relocation, semantic similarity matching for mutations, CRDTs, and automatic merge are excluded.

## Acceptance Criteria

- Exact source spans match LF, CRLF, UTF-8 BOM, headings, paragraphs, fenced code, and surrounding list/blockquote content.
- A fingerprint is exactly 16 lowercase hex characters and changes when exact element source changes, including whitespace or line endings.
- `document` is the canonical unhashed document-root pointer.
- Internal logical pointer forms remain valid and deterministic for a revision.
- Public concrete-element pointers contain fingerprints.
- Read accepts logical navigation pointers and fingerprinted anchors; a unique moved anchor relocates safely.
- Patch requires fingerprints for concrete elements and does not require a client `expectedSourceHash`.
- An unrelated document edit does not block a patch whose target fingerprint is still valid.
- A changed or removed target is rejected unless exact kind-plus-fingerprint relocation identifies one current element.
- Ambiguous relocation is rejected, while a direct logical-pointer-plus-fingerprint match wins over duplicates elsewhere.
- `replace` remains a backward-compatible deprecated alias of `replace_element`; valid existing single-element calls continue to work, while multi-element replacement is rejected.
- `replace_element` accepts exactly one editable replacement element and cannot change a heading level or consume its section body.
- `replace_section` accepts only a fingerprinted heading target, replaces through the next heading with level <= N or EOF, includes nested headings, and rejects replacement content containing a sibling or ancestor heading.
- Replace, section-replace, insert-before, insert-after, and delete preserve untouched source formatting, EOLs, BOM, and whitespace.
- Multiple patch operations are atomic and resolve against the same current source revision.
- Internal write retries are bounded.
- `kb_move` and `kb_delete` retain whole-file `expectedSourceHash` checks.
- Chunks never combine body elements from different heading sections.
- Nested headings produce the expected pointer hierarchy and fingerprinted outline.
