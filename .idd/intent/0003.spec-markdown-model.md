# 0003.spec-markdown-model

## Intent

Markdown documents are parsed from their exact source into logical elements with reliable source spans. Internal logical pointers remain deterministic structural addresses, while public concrete-element anchors carry exact-source `selfHash` and `subtreeHash` revision metadata so semantic edits can distinguish changes to one element from changes to the complete source range owned by a subtree mutation, without persistent element IDs.

## Behavior

Only `.md` files are indexed and mutated. Loading preserves the exact source text, line endings, UTF-8 BOM when present, untouched whitespace, and exact-source SHA-256 `sourceHash`. New files are UTF-8 without BOM. Parsing is source-aware and assigns each exposed element an exact source span sufficient for targeted replacement.

Supported element kinds remain `Document`, `FrontMatter`, `Heading`, `Paragraph`, `CodeBlock`, `ListItem`, `Table`, and `BlockQuote`. In public `kb_read.elements[].kind` JSON they serialize as `document`, `front_matter`, `heading`, `paragraph`, `code_block`, `list_item`, `table`, `block_quote`. The parser must reliably handle headings, paragraphs, fenced code, and front matter; lists and block quotes are first-class source-aware elements without addressable semantic descendants in a quote.

A logical semantic pointer is a deterministic structural address such as `frontmatter`, `p1`, `1`, `1.p1`, or `1.2.p3`. Logical pointers remain the identity stored in parser, chunk, and SQLite structures. They may change after structural edits.

A public anchor for a concrete element has the canonical form `<logical-pointer>~<selfHash>~<subtreeHash>`. Both hashes are XxHash64 over exact UTF-8 source, serialized as exactly 16 lowercase hexadecimal characters. `selfHash` covers the element's own exact parser source span. For leaf elements `subtreeHash == selfHash`; for headings, `subtreeHash` covers the heading and every raw source character up to the next heading with level less than or equal to the current heading, exclusive, or EOF. Whitespace, line endings, Markdown syntax, comments, unsupported raw constructs, case, and trailing spaces are not normalized. The special document-root pointer remains exactly `document` and has no hashes.

The hashes are derived revision metadata, not persistent IDs. SQLite stores `self_hash` and `subtree_hash` as derived index metadata so search anchors describe one indexed revision; source parsing computes the same anchor form for current-source read and outline results. No paragraph UUIDs are introduced. Public `kb_read`, `kb_search`, and `kb_outline` results expose canonical v2 anchors for concrete elements. Legacy `<logical-pointer>~<selfHash>` input remains accepted for navigation and `Self` mutations during the compatibility period, but it is never emitted.

Read/source boundaries are distinct from mutation/hash ownership spans. `kb_read` loads one current `MarkdownSourceDocument` revision from the workspace and derives its Markdown slice, elements, canonical anchors, `NextPointer`, and `sourceHash` from that same source revision. It expands a page start as needed to include Markdown container syntax such as list markers, indentation, task markers, and blockquote prefixes. A page ending before `NextPointer` ends at that next element's read boundary, preserving intervening whitespace and raw Markdown. These read boundaries do not alter `selfHash`, `subtreeHash`, relocation, or section ownership. A stale v2 heading anchor whose `selfHash` still matches may navigate to the current section even when `subtreeHash` changed; subtree validation remains a mutation rule for `replace_section` and `delete_section`, not a read barrier.

Resolution first checks the current element at the logical pointer using exact element kind plus `selfHash`. If both match, that direct match wins even when identical elements exist elsewhere. Otherwise relocation uses only exact element kind plus `selfHash`; `subtreeHash` is never used to identify an element. Exactly one relocation candidate is accepted. Zero candidates are stale, while multiple candidates are ambiguous. Fuzzy matching, edit distance, embeddings, surrounding-context heuristics, and LLM-assisted relocation are excluded.

Image-link destinations are ordinary Markdown text and are updated only through a safe addressable semantic element via `kb_patch` (normally `replace_element`, or intentional `replace_section`). The binary image tools never edit Markdown; cross-file move-plus-patch has no transaction or automatic rollback. Raw link definitions/HTML that cannot be addressed safely are not edited by blindly replacing a whole document.

Semantic patch operations are `replace`, `replace_element`, `replace_section`, `delete_section`, `insert_before`, `insert_after`, and `delete`. Legacy `replace` is a deprecated alias of `replace_element`. `insert_before` and `insert_after` use `Self` scope and validate `selfHash`. `replace`, `replace_element`, and `delete` use `Subtree` scope for ListItem targets and `Self` scope for other element types. `replace_section` and `delete_section` use `Subtree` scope for Heading targets. Subtree operations validate both hashes after safe resolution. Concrete mutations require at least `selfHash`. Both section operations require canonical v2 input with `subtreeHash`; a legacy v1 anchor is rejected with an actionable reread message. `document` remains unhashed and supports only `insert_before` and `insert_after`.

`replace_element` and legacy `replace` replace exactly one concrete editable element from the existing Markdown element model. Their replacement Markdown must parse to exactly one editable element, except that a list-item subtree may contain separately addressable child ListItems when validated within the original document context. When the target is a heading, the replacement must also be a heading of the same level, so element replacement cannot implicitly restructure the document or consume the section body.

`replace_section` requires a v2 heading anchor and replaces the heading plus its complete logical section. For a target heading of level N, the range extends from the target heading source start to the next heading with level <= N, exclusive, or to EOF. Nested headings with level > N belong to the section. The replacement must begin with a heading of the same level; every later heading in the replacement must be deeper than N. Section ranges are computed structurally from the current parsed revision after safe anchor resolution, while the raw source between boundaries is replaced so unsupported or non-indexed constructs inside the section are not left behind.

`delete_section` requires the same v2 heading anchor and uses the same owned section range as `replace_section`, but replaces that range with an empty string. It removes the heading, nested headings, semantic elements, comments, unsupported/raw Markdown, and all other source owned by the section. Supplying `markdown` to `delete_section` is invalid. Plain `delete` remains a Self operation: when aimed at a heading it removes only that heading and preserves the section body.

All operations in one patch resolve against one current source revision and are validated before any write. Resolved duplicate targets, missing or stale anchors, ambiguous relocation, overlapping edits, and contradictory operations reject the whole patch. A section replacement or deletion overlaps every operation whose source range falls inside that section; the next sibling boundary heading itself is outside the section and may be independently edited in the same patch. Source construction replaces or inserts only at validated spans, normalizes replacement EOLs to the current document, preserves BOM and every untouched byte-equivalent character, and does not round-trip the document through an AST serializer.

`sourceHash` is no longer a client concurrency token for `kb_patch`. It remains an internal exact-source guard between reading a patch attempt and atomically replacing the file. If the source changes during that window, the patch retries a bounded number of times from the newest source, including re-parsing and re-resolving all anchors. `sourceHash` also remains available for whole-file operations such as move and delete.

Chunks do not cross document or heading-section boundaries, keep code blocks intact, respect configured byte and element limits within a section, include heading context when configured, and produce stable embedding text hashes. A heading starts a new boundary; body content from two different heading sections cannot share a chunk.

Outline is a deterministic projection of parsed headings containing canonical v2 public pointer, level, title, and nesting.

## Architecture And Patterns

Core defines source documents, logical semantic pointers, public semantic anchors, fingerprinting and resolution rules, elements, chunks, patch DTOs, outline DTOs, parser/validator APIs, and pure source patching rules. Infrastructure provides source loading, source-based Markdown slicing and navigation, SQLite-backed search/index adapters, and mutation orchestration.

`MarkdownSourceDocument` contains relative path, absolute path, exact source Markdown, `SourceHash`, encoding/BOM information, and last-write time. Normalized text may be derived for hashing/search compatibility but cannot replace exact source for editing.

The SQLite `elements.pointer` and `chunks.pointer` values remain logical pointers. Derived `elements.self_hash` and `elements.subtree_hash` are computed from the same indexed source revision during parse/indexing. Schema version 4 rebuilds an older derived index that lacks these columns; source Markdown remains authoritative.

## Non-goals

Persistent element identities, full general-purpose Markdown editor AST serialization, fuzzy relocation, semantic similarity matching for mutations, CRDTs, and automatic merge are excluded.

## Acceptance Criteria

- Exact source spans match LF, CRLF, UTF-8 BOM, headings, paragraphs, fenced code, and surrounding list/blockquote content.
- `selfHash` and `subtreeHash` are each exactly 16 lowercase hex characters; exact whitespace, syntax, and line-ending changes inside their respective ranges change the hash.
- `document` is the canonical unhashed document-root pointer.
- Internal logical pointer forms remain valid and deterministic for a revision.
- Public concrete-element pointers use canonical `logical~selfHash~subtreeHash`; leaf elements have equal hashes.
- Read accepts logical navigation pointers, legacy v1 anchors, and canonical v2 anchors; a unique moved anchor relocates safely by kind plus `selfHash`.
- Patch requires `selfHash` for concrete elements, requires `subtreeHash` for `replace_section` and `delete_section`, and does not require a client `expectedSourceHash`.
- An unrelated document edit does not block a `Self` patch whose target `selfHash` is still valid.
- A changed or removed target is rejected unless exact kind-plus-`selfHash` relocation identifies one current element.
- Ambiguous relocation is rejected, while a direct logical-pointer-plus-`selfHash` match wins over duplicates elsewhere.
- `replace` remains a backward-compatible deprecated alias of `replace_element`; valid existing single-element calls continue to work, while multi-element replacement is rejected.
- `replace_element` accepts exactly one editable replacement element and cannot change a heading level or consume its section body.
- `replace_section` accepts only a v2 heading target, validates the exact owned source range through the next heading with level <= N or EOF, includes raw/non-indexed content and nested headings, and rejects stale subtree state.
- `delete_section` uses that same v2 heading target and owned source range, rejects stale subtree state, forbids `markdown`, and removes the complete section while plain `delete` remains Self-scoped.
- Replace, section-replace/delete, insert-before, insert-after, and delete preserve untouched source formatting, EOLs, BOM, and whitespace.
- Multiple patch operations are atomic and resolve against the same current source revision.
- Internal write retries are bounded.
- `kb_move` and `kb_delete` retain whole-file `expectedSourceHash` checks.
- Chunks never combine body elements from different heading sections.
- Nested headings produce the expected pointer hierarchy and canonical v2 outline anchors.

### ListItem and opaque BlockQuote ownership

Each Markdig list item outside a quote is one `list_item` element, independently addressable by `li1`, `1.li2`, or `1.li2.li1`. Root/section siblings have their own counters and each parent independently numbers direct children. No semantic List container or separate TaskListItem is exposed. The item's own Markdown includes its physical marker, indentation and all own paragraphs/code, including own content following descendants. Nested items have their own elements and are excluded from parent Text.

An isolated Markdig QuoteBlock is one completely opaque `block_quote` element at `q1` or `1.q2`. It owns all original source including every `>` prefix; no heading, list item, paragraph, code, or second quote inside it is published. A quote inside a ListItem is only part of the item's own text. Quote text is indexed once. Quote `selfHash == subtreeHash`.

The shared internal source map distinguishes own noncontiguous source segments, subtree, replacement and physical deletion ranges, insertion boundaries, parent/depth, and list-container marker style. The ListItem self fingerprint covers the exact own segments, with count and byte lengths to delimit discontinuous segments; its subtree fingerprint covers the exact full physical subtree. A leaf has identical fingerprints. Adding or deleting children must not change the parent's self fingerprint.

To preserve legacy positions where possible, inner paragraphs and code consume virtual `pN`/`codeN` counters but do not become addressable; the suppressed positions are reserved and reject older hashed anchors rather than relocating them to unrelated ordinary text.

`delete` and `replace_element`/`replace` for ListItem are subtree mutations: both hashes are required, and the whole item and descendants are removed/replaced. Adjacent insertion checks only self hash and inserts one sibling at the same indentation/marker style. BlockQuote mutations use self hash and target the whole opaque quote. Heading and section mutation scopes remain unchanged. Source edits validate the resulting Markdig structure before any atomic write; unsafe containers and invalid indentation fail without modifying source.


### Semantic GFM pipe tables

Markdig 1.4.0 with the shared strict GFM pipe table pipeline parses standalone tables into atomic `Table` elements. Their logical pointers are `tN` at document root or `section.tN` in headings; `selfHash` and `subtreeHash` both cover the table's exact source characters. Cell and row AST descendants have no independent semantic pointers, and tables nested inside lists and quotes remain owned by the enclosing opaque or list item element. Previous paragraph ordinals occupied by tables must be reserved to prevent silently reassigning old `pN` pointers.

Addressing a table through `kb_read` returns structured `table` metadata in addition to the original source: declared column count, data-row count, zero-based column names and alignments, and zero-based arrays of rendered cell text. Missing physical data cells appear empty; extra physical cells do not appear in the logical projection. The entire structure comes from the source revision associated with `sourceHash`.

Table-specific semantic writes use `kb_edit_table` instead of rebuilding a Markdown string on the client. Seven actions support updates of one or more cells, insertion/deletion of rows or columns, column renaming and alignment. Row `where` and column-name selection use exact ordinal equality; ambiguous matches cause conflict. A canonical v2 hashed pointer and current table self hash are mandatory. Changed cells are replaced by source ranges; whole-table-range rebuilding is permitted for structural column changes. Text values are escaped as literals; inline Markdown formatting requires explicit `valueFormat=markdown`. Edits with extra ignored physical cells are rejected. The editor reparses and structurally validates the result, then reuses existing atomic source-file commits and index reconciliation. The returned pointer is resolved from the newly parsed committed revision, allowing chained writes. `kb_patch` is still used to delete an entire table.
