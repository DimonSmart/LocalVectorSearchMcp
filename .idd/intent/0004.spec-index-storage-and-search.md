# 0004.spec-index-storage-and-search

## Intent

SQLite is a derived index of Markdown source files and serves consistent lexical, semantic, and hybrid retrieval, including path-scoped search and automatic reconciliation after MCP or watched filesystem changes.

## Behavior

Each server instance stores its project's documents, Markdown elements, chunks, FTS5 rows, sqlite-vec vectors, and manifest metadata in one SQLite database. SQLite never becomes the source of truth for mutations. Documents store exact-source hashes; searchable chunks store body text plus heading-path text used by lexical retrieval. The current schema version is `4`; older schemas are incompatible and require the existing forced-rebuild mechanism rather than complex vector migration.

Deletion removes document, element, chunk, FTS, and vector rows consistently. sqlite-vec initialization, native runtime packaging, manifest compatibility, dimension validation, and forced-rebuild behavior continue to follow ADR 0006 and the existing index invariants.

Changed/all reindex discovers configured Markdown sources, preserves old indexed content when processing a changed file fails, and removes missing or excluded files. If the embedding provider is unavailable, reindex stops cleanly, reports a warning instead of surfacing an unhandled MCP exception, and marks the failing path dirty when synchronization state is available. Successfully indexed content remains available for lexical search. A targeted source reconciliation operation indexes or deletes one path without scanning the whole workspace and preserves the previous indexed version if replacement indexing fails.

Successful MCP create, patch, move, and delete commit the source mutation before scheduling targeted index reconciliation. A successful source commit returns deterministically without waiting for embedding or other potentially slow index work; its response reports `indexSynchronized = false` while reconciliation is pending. The affected path is marked dirty/out-of-sync until synchronization completes. If reconciliation fails, the source remains authoritative, status exposes the failure, and the product does not roll back the user's source file because an embedding or index provider failed.

Optional watching observes external Markdown create/change/delete/rename events under the configured root. Events are debounced and then enter the same targeted synchronization scheduler used by MCP mutations. The scheduler coalesces repeated changes per path, tracks a monotonically newer generation/token for each scheduled revision, and guarantees that completion of an older reconciliation cannot clear pending state for a newer change. A change that arrives while one reconciliation is running causes one later reconciliation for the latest generation; intermediate revisions need not all be indexed. A transient watcher or reconciliation failure does not terminate the MCP server: previously valid indexed content remains, dirty state and the last error are visible through status, and a later mutation/filesystem event or explicit reindex may recover it. No periodic infinite retry loop is required.

Lexical search uses parameterized FTS5/BM25 over body text and heading path. Vector search uses sqlite-vec. Hybrid search uses Reciprocal Rank Fusion when embeddings are available. Embedding-provider unavailability is a recoverable capability loss for hybrid search: hybrid falls back to lexical retrieval, returns the lexical results as such, and includes an explicit warning that semantic search is unavailable. Explicit semantic mode does not silently change semantics and returns a controlled tool error instead. Optional include/exclude search globs filter indexed document paths inside each retrieval query; filtering occurs before TopK selection in lexical, semantic, and hybrid modes. `TopK` therefore means results within scope, never unscoped results filtered afterward.

`kb_read` is not an indexed read. It loads one current source revision from the workspace and returns its exact `sourceHash`, source-derived elements/anchors, and existing inclusive slice/pagination behavior without waiting for embeddings or index reconciliation. `kb_search` remains eventually consistent: every result carries `indexedSourceHash` from the same indexed document revision as its snippet and semantic anchor, and that hash may differ from the current source revision.

## Architecture And Patterns

Infrastructure owns SQLite and filesystem adapters, source-based Markdown slicing, schema/manifest compatibility, revision-aware targeted index reconciliation, status/dirty-state tracking, watcher hosting, FTS/vector scope filtering, and mutation orchestration. Core owns DTOs, ranking, exceptions, and narrow application service interfaces. Search/read/patch/create/move/delete/list/outline services do not depend on MCP classes.

## Non-goals

Manual production vector scans, separate embedding-cache tables, direct score normalization, automatic background retry loops, and treating assets as embedding documents are excluded.

## Acceptance Criteria

- SQLite schema version is `4`, with aligned chunk/FTS/vector row ids, exact document source hashes, and searchable heading context.
- A schema-2 or older index is incompatible without force and recreates correctly with force.
- Lexical heading-only queries find matching sections.
- Lexical, semantic, and hybrid include/exclude scopes are applied before TopK.
- Reindex and targeted reconciliation preserve old indexed content when replacement indexing fails.
- Embedding-provider failure does not terminate hybrid search: hybrid returns lexical results plus a warning, while explicit semantic search returns a controlled error.
- Reindex stops cleanly with a warning when embeddings are unavailable instead of exposing an unhandled MCP exception.
- Create, patch, move, and delete return a successful committed source revision without waiting for slow index work; callers can distinguish pending or failed index synchronization with `indexSynchronized` and status.
- Source-success/index-pending or index-failure results mark dirty status without rolling back source; `kb_read` immediately observes the committed source while `kb_search` may keep the previous indexed revision until reconciliation, after which search reflects the latest revision and deletion leaves no related rows.
- External create/edit/rename/delete is reconciled through the same scheduler when watching is enabled; rapid events coalesce, stale completion cannot clear a newer pending generation, and assets are ignored.
- Watcher failures do not terminate the server, preserve the last valid indexed revision, and appear in status.
- Existing source slice limits and pagination remain compatible, reads include the exact current-source `sourceHash`, and search results include `indexedSourceHash`.

## Verification

- Integration-test schema/manifest compatibility, FTS heading queries, vector operations, scoped retrieval, targeted create/replace/move/delete reconciliation, and deletion consistency.
- Integration-test asynchronous mutation reconciliation, source-success/index-pending or index-failure dirty state, watcher create/edit/rename/delete/coalescing, and status recovery.
- Unit-test RRF and glob-scope behavior.
- Integration-test hybrid fallback and explicit semantic failure with an unavailable embedding provider.
