# 0004.spec-index-storage-and-search

## Intent

SQLite is a derived index of Markdown source files and serves consistent lexical, semantic, and hybrid retrieval, including path-scoped search and automatic reconciliation after MCP or watched filesystem changes.

## Behavior

Each server instance stores its project's documents, Markdown elements, chunks, FTS5 rows, sqlite-vec vectors, and manifest metadata in one SQLite database. SQLite never becomes the source of truth for mutations. Documents store exact-source hashes; searchable chunks store body text plus heading-path text used by lexical retrieval. The current schema version is `3`; older schemas are incompatible and require the existing forced-rebuild mechanism rather than complex vector migration.

Deletion removes document, element, chunk, FTS, and vector rows consistently. sqlite-vec initialization, native runtime packaging, manifest compatibility, dimension validation, and forced-rebuild behavior continue to follow ADR 0006 and the existing index invariants.

Changed/all reindex discovers configured Markdown sources, preserves old indexed content when processing a changed file fails, and removes missing or excluded files. A targeted source reconciliation operation indexes or deletes one path without scanning the whole workspace and preserves the previous indexed version if replacement indexing fails.

Successful MCP create, patch, move, and delete synchronously reconcile the index before returning. If the source mutation succeeds but index reconciliation fails, the source remains authoritative, the response explicitly reports that indexing failed, and the path is marked dirty/out-of-sync. The product does not roll back the user's source file because an embedding or index provider failed.

Optional watching observes external Markdown create/change/delete/rename events under the configured root. Events are debounced/coalesced, reconcile only affected Markdown paths, and do not embed assets. Events resulting from MCP writes are harmlessly deduplicated using current source/index state. A transient watcher failure does not terminate the MCP server: previously valid indexed content remains, dirty state and the last error are visible through status, and explicit reindex remains the recovery mechanism. No infinite retry loop is required.

Lexical search uses parameterized FTS5/BM25 over body text and heading path. Vector search uses sqlite-vec. Hybrid search uses Reciprocal Rank Fusion. Optional include/exclude search globs filter indexed document paths inside each retrieval query; filtering occurs before TopK selection in lexical, semantic, and hybrid modes. `TopK` therefore means results within scope, never unscoped results filtered afterward.

Indexed reads return exact current `sourceHash` with the existing inclusive semantic slice and pagination behavior. Reads must not silently claim synchronization when the source file differs from the indexed revision.

## Architecture And Patterns

Infrastructure owns SQLite and filesystem adapters, schema/manifest compatibility, targeted index reconciliation, status/dirty-state tracking, watcher hosting, FTS/vector scope filtering, and mutation orchestration. Core owns DTOs, ranking, exceptions, and narrow application service interfaces. Search/read/patch/create/move/delete/list/outline services do not depend on MCP classes.

## Non-goals

Manual production vector scans, separate embedding-cache tables, direct score normalization, automatic background retry loops, and treating assets as embedding documents are excluded.

## Acceptance Criteria

- SQLite schema version is `3`, with aligned chunk/FTS/vector row ids, exact document source hashes, and searchable heading context.
- A schema-2 or older index is incompatible without force and recreates correctly with force.
- Lexical heading-only queries find matching sections.
- Lexical, semantic, and hybrid include/exclude scopes are applied before TopK.
- Reindex and targeted reconciliation preserve old indexed content when replacement indexing fails.
- Create, patch, move, and delete are visible to the immediately following search/read; deletion leaves no related rows.
- Source-success/index-failure results are explicit and mark dirty status without rolling back source.
- External create/edit/rename/delete is reconciled when watching is enabled; rapid events coalesce and assets are ignored.
- Watcher failures do not terminate the server, preserve the last valid indexed revision, and appear in status.
- Existing slice limits and pagination remain compatible, and reads include `sourceHash`.

## Verification

- Integration-test schema/manifest compatibility, FTS heading queries, vector operations, scoped retrieval, targeted create/replace/move/delete reconciliation, and deletion consistency.
- Integration-test mutation visibility, source-success/index-failure dirty state, watcher create/edit/rename/delete/coalescing, and status recovery.
- Unit-test RRF and glob-scope behavior.
